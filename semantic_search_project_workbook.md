# Проект: семантический поиск товаров по текстовому запросу (query-to-item)

> Рабочий документ проекта. Код и все вычисления — в тетради `semantic_search_project.ipynb`; каждое число ниже взято из выполненной ячейки тетради (указан раздел).

---

## О проекте

**Бизнес-контекст.** Компания CalmFruits развивает онлайн-каталог товаров. Пользователи ищут товары через поисковую строку, но классический поиск по ключевым словам не всегда справляется с реальными запросами.

**Гипотеза.** Поиск можно улучшить с помощью векторных представлений запросов и товаров. Для проверки строится MVP системы семантического поиска.

**Данные.** Сырой каталог `wb_products_raw_sample.parquet`, пул асессоров `wb_products_dedup.parquet` (список `imt_id` для каталога оценки), разметка `queries_synthetic_train.parquet` и `queries_synthetic_test.parquet` (только для одного финального прогона).

**Итоговые артефакты проекта:**

- тетрадь `semantic_search_project.ipynb` с EDA, пайплайном, экспериментами, финальной оценкой и выводами;
- эксперимент `calmfruits_semantic_search` в MLflow;
- этот документ;
- Streamlit-приложение — дополнительное задание, не выполнялось (не влияет на зачёт).

---

# Неделя 1. Знакомство с проектом и данными

## Задача

- Query-to-item: по короткому текстовому запросу вернуть top-K карточек товара `imt_id`.
- Сравниваются два подхода с одинаковым интерфейсом: лексический baseline (TF-IDF) и семантический поиск (эмбеддинги MiniLM).
- Решение принимается по метрикам на разметке и по качественному разбору ошибок.

---

## 1. Наблюдения по данным (EDA)

- **Размер и структура** (раздел 2.1): 200 000 строк, 174 427 `imt_id`, 199 957 `nm_id`, полных дубликатов нет; 25 573 строки повторяют карточку; у 1 606 карточек различаются названия, у 1 274 — описания.
- **Полнота полей** (раздел 2.2): `NaN` нет, пропуски закодированы пустыми строками. `description` пуст у 28,75% строк, `nm_colors_names` — у 17,11%, `imt_name` — у 0,35%, `brand_name` — у 0,10%, `subj_name` — у 8 строк; без названия и описания одновременно — 163 строки.
- **Категории** (раздел 2.3): крупнейшие корни — «Одежда» (43 316 строк), «Аксессуары» (16 446), «Дом» (15 024), «Обувь» (13 187); 3 233 предметные категории, 525 из них с одной карточкой.
- **Длина текстов** (раздел 2.4): название — медиана 4 слова, 99% не длиннее 15 слов; описание — медиана 53 слова, 95-й перцентиль 188, 99-й — 321, максимум 754 слова.
- **Качество текста** (раздел 2.5): HTML в 22 описаниях; спецсимволы в 13,27% названий, длинные буквенно-цифровые токены в 7,44%; технические обозначения смысловые (`R 8.6`, `TORX T70`); многие названия общие («Костюм», «Платье»).
- **Бренд и цвет** (раздел 2.6): 13 318 брендов; цвет встречается в названии у 3,94% строк, где заполнены и название, и цвет.
- **Разметка train** (раздел 2.7): 11 453 пары, 700 запросов, 2 285 товаров; медиана 16 оценённых товаров на запрос; оценки 1 — 9 652, 2 — 1 101, 3 — 700, нулей нет; у каждого запроса есть товар с оценкой ≥ 2, в медиане — один (неделя 2, раздел 4).
- **Согласованность** (раздел 1): все `item_id` train и test есть в каталоге; запросы train и test не пересекаются ни по `query_id`, ни по тексту.
- **Запросы** (раздел 2.7): короткие — тип товара с атрибутом или брендом («кожаные мокасины», «топы cop copine»).

**Принятые решения недели 1** (раздел 2.8): индекс по `imt_id`; категории «Одежда» и «Обувь» — только у них есть релевантные train-запросы; `product_text = imt_name . subj_name . description`; карточки без описания остаются с признаком `has_description`; порог `relevance >= 2`, K = 1, 3, 5, 10.

# Неделя 2. Базовый пайплайн поиска. Первое ревью

## 2. План базового пайплайна

**2.1. Формулировка задачи**

По короткому запросу пользователя ищем карточки одежды и обуви в подготовленном каталоге и возвращаем top-K. Качество оцениваем по синтетической разметке train (golden-сет — validation-часть), метриками ранжирования при фиксированных пороге и K. Бизнесу это нужно, чтобы понять, окупится ли переход на векторный поиск.

**2.2. Подготовка данных** (неделя 2, раздел 1)

Фильтр категорий → очистка текста → отсев карточек без названия и описания → дедупликация по `imt_id` (самое длинное описание, затем меньший `nm_id`) → `product_text` и `has_description`. Итог — 48 376 карточек; у 62,6% из них нет описания. Очистка изменила 5 123 карточки.

**2.3. Лексический поиск (baseline)** (раздел 2)

TF-IDF по `product_text`: униграммы и биграммы, до 50 000 признаков, L2-нормализация, косинусное сходство; запрос проходит ту же очистку. Функция `search_lexical(query, top_k)`.

**2.4. Семантический поиск** (раздел 2)

`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (фиксированная ревизия), 384 измерения; товары и запросы кодируются одной моделью, батчами, с `normalize_embeddings=True`; эмбеддинги сохраняются в `.npy`; поиск — полный перебор. Функция `search_semantic(query, top_k)`. Лимит 128 токенов обрезает 12,7% текстов каталога MVP.

**2.5. Оценка качества** (разделы 3–4)

Метрики реализованы с явным порогом `RELEVANCE_THRESHOLD = 2`, NDCG по шкале 0–3, неразмеченные товары — нерелевантные; формулы проверены на контрольных сценариях. Train разбит на 560 development- и 140 validation-запросов с группировкой по тексту запроса; golden-сет — 2 281 пара validation. По всему каталогу MVP (48 376 карточек) лишь 13,5% топ-10 размечены и NDCG@10 = 0,090 на 100 development-запросах; по пулу асессоров (4 256 карточек) — 83,6% и 0,442. Поэтому каталог оценки — пересечение подготовленного каталога с пулом.

**2.6. Результаты базового сравнения** (раздел 5)

| Метод (validation, 4 256 карточек) | NDCG@10 | MRR | Recall@10 | P@1 | HitRate@10 |
| --- | ---: | ---: | ---: | ---: | ---: |
| TF-IDF | 0,459 | 0,169 | 0,320 | 0,071 | 0,450 |
| MiniLM | 0,231 | 0,117 | 0,171 | 0,050 | 0,257 |

- Лексический поиск лучше по всем метрикам и при всех K.
- Семантика чаще выдаёт неразмеченные товары (размечено 39,9% её топ-10 против 85,4%), часть её ошибок может быть неоценёнными подходящими товарами.
- Карточки без описания — 22,5% каталога оценки, но 90,7% первых позиций TF-IDF и 83,6% MiniLM; релевантных среди них в golden-сете нет. Это главная причина низких P@1 и MRR.
- Расхождения: «шубы искусственные с капюшоном», «босоножки deezee», «детские полуботинки» — TF-IDF ставит товар с оценкой 3 первым, MiniLM возвращает другие типы товаров (кофточки, дутики, кроссовки).

**2.7. Выявленные проблемы**

- Перекос выдачи в сторону коротких карточек без описания.
- Семантическая модель не удерживает тип товара и путает смежные категории.
- Метрики занижены неполной разметкой.

# Недели 3–4: Улучшение системы. Второе ревью

## 3. Эксперименты по улучшению

Все эксперименты — на одном golden-сете (140 validation-запросов), каталоге из 4 256 карточек, пороге `relevance >= 2` и K = 1, 3, 5, 10; подбор параметров и обучение — только на 560 development-запросах.

**Эксперимент 1 — короткий текст для эмбеддингов**
- Гипотеза: MiniLM обрезает 27,6% полных текстов пула; шаблон `imt_name . subj_name` помещается в лимит и сохраняет смысловое ядро.
- Что меняем: только шаблон `product_text` семантического поиска.
- Результат: NDCG@10 0,231 → 0,188; MRR 0,117 → 0,144; Recall@10 0,171 → 0,214.
- Вывод: по ключевой метрике гипотеза отклонена — описания нужны для градуированного ранжирования.

**Эксперимент 2 — гибрид RRF**
- Гипотеза: объединение выдач сохранит точные совпадения TF-IDF и добавит находки семантики.
- Что меняем: способ ранжирования — RRF с весом семантики `alpha`, подобранным на development (0,1).
- Результат: NDCG@10 0,460 против 0,459 у TF-IDF; Recall@10 0,339 против 0,320; P@5 0,069 против 0,063; MRR 0,157 против 0,169.
- Вывод: подтверждена частично — полнота выросла, NDCG@10 практически равен baseline.

**Эксперимент 3 — дообучение: линейная проекция поверх замороженного MiniLM**
- Гипотеза: проекция, обученная triplet loss на парах development, адаптирует пространство к домену.
- Что меняем: запросы и товары проходят одну обученную проекцию 384×384.
- Результат: 7 168 троек; NDCG@10 0,231 → 0,096; MRR 0,117 → 0,136.
- Вывод: отклонена — проекция не переносится на новые запросы по ключевой метрике.

## 4. Трекинг экспериментов в MLflow

Эксперимент `calmfruits_semantic_search`; runs `lexical_tfidf`, `semantic_minilm_full_text`, `semantic_minilm_short_text`, `hybrid_rrf`, `semantic_minilm_projection` (validation) и `hybrid_rrf_final_test` (test). В каждом залогированы параметры (метод, `eval_split`, размер каталога, порог, K, seed, модель, шаблон текста, параметры TF-IDF/RRF/проекции, отпечаток протокола), все метрики и артефакты: метрики по запросам, сводная таблица, график сравнения, копия golden-сета. Скрипт `check_mlflow.py` проходит без замечаний (раздел 3 недели 3).

## 5. Финальная оценка и выводы для бизнеса

**5.1. Итоговая таблица**

| Конфигурация | Выборка | NDCG@10 | MRR | P@1 | P@5 | Recall@10 | HitRate@10 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **RRF-гибрид (выбран)** | validation | **0,460** | 0,157 | 0,050 | 0,069 | 0,339 | 0,450 |
| TF-IDF (baseline) | validation | 0,459 | 0,169 | 0,071 | 0,063 | 0,320 | 0,450 |
| MiniLM, полный текст | validation | 0,231 | 0,117 | 0,050 | 0,049 | 0,171 | 0,257 |
| MiniLM, короткий текст | validation | 0,188 | 0,144 | 0,079 | 0,063 | 0,214 | 0,286 |
| MiniLM + проекция | validation | 0,096 | 0,136 | 0,093 | 0,059 | 0,146 | 0,229 |
| **RRF-гибрид** | **test** | **0,424** | 0,152 | 0,047 | 0,059 | 0,296 | 0,407 |

Выбор — по NDCG@10 (единственная метрика, использующая шкалу 0–3), затем MRR; правило зафиксировано до сравнения. Отрыв гибрида от TF-IDF на validation — 0,0007, то есть гибрид по качеству равен лексическому поиску и чуть полнее его. Test (300 запросов) прогнан один раз.

**5.2. Качественный анализ ошибок**

- Бренда нет в тексте товара: «футболки lovetex store» — в выдаче футболки других брендов (NDCG@10 = 0).
- Бренд перевешивает тип: «анораки puma» — кроссовки и леггинсы PUMA, худи, футболка, куртка вместо анорака (NDCG@10 = 0).
- Атрибут игнорируется: «костюмы на пуговицах» — костюмы вообще, плащ, платье (NDCG@10 = 0,073).
- Семантика в чистом виде путает смежные категории (дутики вместо босоножек, кофточки вместо шуб) и теряет тип товара при незнакомом бренде.
- Короткие карточки без описания занимают большинство первых позиций.

**5.3. Рекомендация бизнесу**

Заменять поиск по ключевым словам векторным не стоит: на каталоге одежды и обуви чистый семантический поиск вдвое хуже по NDCG@10. Имеет смысл развивать только гибрид с небольшим весом семантики: он не хуже текущего подхода и немного чаще приводит в топ-10 подходящие товары. Прирост мал, поэтому внедрять — после A/B-теста на реальных пользователях. Гибрид полезен для запросов с типом товара и неточными словами и ошибается на брендах и конкретных атрибутах. Главный резерв качества — сам каталог: у 62,6% карточек нет описания.

**5.4. Дальнейшие шаги**

1. Понизить вес карточек без описания или обогатить их текст атрибутами; мотивировать продавцов заполнять описания.
2. Бренд и атрибуты — отдельными полями и фильтрами поверх выдачи.
3. Реальные логи запросов, кликов и покупок; доразметка популярных неоценённых товаров.
4. Русскоязычная модель или модель с большим окном, дообучение на логах с разбиением по тексту запроса без утечки.
5. ANN-индекс (FAISS, HNSW) при росте каталога с контролем полноты относительно точного поиска.
